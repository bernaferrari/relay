## How the launch spreads beyond one post

The founder's continuation posts make the product legible in layers. One [shows deterministic checks and agent goals together](https://x.com/o_kwasniewski/status/2105675146979848466); another [names web/mobile and tags Kernel and Expo](https://x.com/o_kwasniewski/status/2105675150246953434); another [tags AI SDK, Vercel, and existing model subscriptions](https://x.com/o_kwasniewski/status/2105675153203920934). The [thread's final post](https://x.com/o_kwasniewski/status/2105675155720552843) repeats the setup command and asks for a GitHub star. These are observable ecosystem entry points. Tagging alone does not establish why another account amplified it.

Expo provides a substantive [official integration guide](https://docs.expo.dev/guides/using-e2e/), including local setup and hosted EAS execution. This gives mobile developers a route from attention into their existing environment. The guide distinguishes the framework from the separately hosted TesterArmy platform and explicitly says no TesterArmy account is needed for e2e.

The [e2e landing](https://tester.army/e2e) displayed a 2,305-star GitHub link and a testimonial section with nine visible linked X posts plus a “Show More (24)” control. The visible authors include Rauch, Expo, Cramer, Michał Pierzchała, and Jean-Michel Lemieux. This is an observed social-proof surface, not proof that each author adopted the framework. The [repository](https://github.com/tester-army/e2e) separately provides examples, npm package links, docs, Discord, and contribution instructions.

The sequence is therefore wider than “make a better video”: founder launch, explanatory thread, ecosystem quotes, partner documentation, creator interpretation, adoption follow-ups, and landing proof. Their individual contribution to reach is unknown.

## What the adoption path actually requires

The [landing page](https://tester.army/e2e) begins with a human/agent choice, setup command, and small test example. Clicking the agent choice changed the command to `npx skills add tester-army/e2e`. Configuration options and generated configuration are further down. This gives both people and coding agents a concrete entry point.

The [quickstart](https://e2e.tester.army/docs/quickstart) requires Node 22.12+, WSL on Windows, and target tooling. Mobile needs Xcode/simulator or Android SDK/emulator. The wizard allows no model and generates an example whose first run only opens an app and checks it. It documents later provider connection and agent steps separately. The setup command is short; the prerequisites remain real. This research did not time setup or execute the framework.

For an existing Expo app, the [Expo guide](https://docs.expo.dev/guides/using-e2e/) additionally instructs developers to build and install a release app, identify the target, write a test, run it, and read evidence. Its later EAS steps build/install on a worker and upload results. Cached agent actions need their recordings available on that worker, and accessibility differences can trigger live reasoning. A local demonstration cannot establish the same cost or behavior in CI.

The [repository README](https://github.com/tester-army/e2e) leads with a familiar TypeScript test that combines a goal and an exact check. It links actual published packages and states the APIs are still developing before 1.0. It says installed docs are included in the npm package for agents to read offline. The framework is Apache 2.0; it should be kept separate from the company's hosted service when making comparisons.

## Concrete launch and product lessons

These are recommendations inferred from the observed launch, not causal findings about Relay's absent analytics.

1. Prepare one shareable promise and one executable proof. A suitable candidate is “Record a test. Run it again. Review what changed.” Make it accurate for a named app and qualified target, and show the actual defect detected, repeated-run timing, and model use. Use the existing public installation path only after it is qualified.
2. Build the first audience's adoption route before a broad launch. Choose one developer ecosystem where Relay solves a real task; publish a working guide, reproducible fixture, agent entry point, and failure recovery. The observed Expo guide offers a stronger pattern than tags alone.
3. Create a distribution packet that a developer or ecosystem maintainer can use: short static announcement, small code/recording example, real result, concise demo, docs link, and honest limitations. Creator explanations and partner quotes can present the same evidence in their audience's language. Human outreach or public posting would require separate user authorization.
4. Make setup succeed before optional model access. Keep the first result independent of a paid model, expose prerequisites, and make the installed example runnable. Check commands and generated snippets from a fresh user environment before publicity.
5. Answer the objections visibly: cost of repeat runs, exact checks, false-positive resistance, supported targets, failure evidence, and reason to prefer Relay for a specific workflow. Feature additions alone do not answer these questions.
6. Measure distribution and adoption separately. Track post/link exposure, successful setup, first saved test, first replay, completed review, and later repeat use using appropriate privacy choices. Test the content promise and adoption path with fresh users. No view target guarantees conversion.

This audit does not establish that Relay lacks each capability. That requires matching its current product and release evidence to these task-level demands. It does establish that the competitor launch offered a clear, open, executable invitation and had observed distribution through relevant people and ecosystem documentation.
